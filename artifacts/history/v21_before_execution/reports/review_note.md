# Discussion note: selection follows display order in a bounded local-model pilot

**We now have a controlled selection-behavior result:** all nine new Qwen2.5-0.5B-Instruct responses selected exactly the first ten displayed candidates. Reversing display order replaced all ten selected configurations; changing ID assignments while keeping feature order retained all ten. This held for the three preselected development cases—MySQL, lrzip and Brotli—with a fresh baseline for each. The same simple display rule reproduces every response. A later post-hoc audit found that continuing an ascending/descending ID sequence also matches all24 V8/V19 outputs, because only monotone ID orders were tested. Thus display-order dependence is observed but the internal selection rule is not uniquely identified. [Rule audit](rule_identifiability_v20.md). [V19 report and figure](order_probe_v19.md).

The nine calls actually ran under a frozen protocol, with unchanged acquired observations/candidate features, counterbalanced condition order, pinned local model, greedy CPU inference, and the same distinct-ID grammar. Every output/token trace and transformation was verified. All nine completed;140 tests now pass. This supports display-order dependence for these conditions. It does not establish a universal model bias, an internal mechanism, statistical generalization, or improved optimization. No new configuration outcomes were acquired or scored in this probe.

The original research question remains: after10 cheap configuration evaluations, can a controller predict whether an LLM should spend the remaining10? The repository has not demonstrated a useful benefit router. Three pieces of evidence explain that result:

1. V8's15 original selections were exactly reproduced by choosing IDs0–9. V19 separates display position from ID assignment for three fixed cases; low numeric IDs alone do not explain the new responses. V9's exhaustive uniform-subset comparison already showed random subsets matching/beating each original model score with probability at least0.5, a conditional reference rather than a significance test. [V8](pilot_report_v8.md), [V9](concrete_result.md).
2. On V6's three held-out families, development-selected benefit/uncertainty policies chose no escalation. Always escalating was worse on average. With a selected rate of zero, matched-rate policies coincide; this does not demonstrate useful discrimination at a nonzero escalation rate. Three test families cannot establish broad learned-router generalization. [V6](pilot_report_v6.md).
3. Actual local compression collection was successful, but those development tasks offered little recorded improvement even from their initial reference: at most2.929%/0.987%/0% on the expanded grid. This finite-table bound explains why larger candidate counts did not create substantial opportunity. It uses offline hindsight and cannot enter router features. Timing noise, constraints and a small workload limit interpretation. [V17](expanded_grid_v17.md), [V18](checkpoint_opportunity_v18.md).

A defensible small report could center on the observed display-rule equivalence, the controlled interventions and the need to establish task headroom before interpreting routing results. The finding is specific to a tiny local model, this prompt/grammar, three exposed cases and one response per condition. More permutations, stronger models, other prompts and quality consequences remain untested. Novelty/publication potential has not been established; the broader escalation hypothesis remains unresolved.

SNAP2 already discusses conditional escalation, so that idea alone is not a novelty claim. Its exact artifact was not located in the bounded audit; this repository's changed-model/classical implementations are adaptations, not a numerical replication. [Source audit](source_audit.md).
